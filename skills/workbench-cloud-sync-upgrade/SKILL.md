# 工作台 CloudBase 数据升级

把已有网页或 WorkBuddy 项目中用户选定的页面/模块数据接入 CloudBase。先认识整个项目，再让用户选范围；不要把整项目、固定业务模块或某一种访问方式当作前提。

## 使用原则

- 先扫描，后提案，再修改。扫描阶段只读代码、配置和现有数据说明，不改项目或云端资源。
- 只迁移用户选中的模块。未选模块继续使用原来的存储方式，并说明它们与已选模块之间的联动影响。
- 文档型数据库和 MySQL 都是可选方案。先依据数据结构给出推荐，再让用户确认或改选。
- 页面部署后直接通过项目入口（通常是 `index.html` 或部署地址）使用；如果项目本来已有登录或权限系统，沿用并检查它与云端数据的关系，不额外生成同步码或分享入口。
- 不要求固定的框架、存储介质、单文档模型、测试环境或无登录方案。生产数据、敏感数据和破坏性迁移需要在方案中标出风险并取得相应确认。

## 阶段一：扫描整个项目

先输出“项目数据扫描表”，不要改代码。至少检查：

| 项目 | 要查内容 |
|---|---|
| 项目入口 | 框架、启动/构建命令、入口文件、部署方式 |
| 页面范围 | 路由、页面、组件、页面间联动 |
| 数据来源 | localStorage、IndexedDB、mock JSON、状态库、现有 API 或其他持久化 |
| 读写位置 | 初始化、查询、新增、编辑、删除、排序、勾选和批量操作分别在哪里 |
| 数据模块 | 模块名称、字段、嵌套结构、关联关系、默认数据、数据量和查询需求 |
| 现有数据层 | 是否已有 store/repository/service；页面是否绕过它直接读写 |
| 外部依赖 | 已有登录、权限、API、文件上传、环境变量和 CloudBase 连接状态 |
| 风险 | 敏感数据、生产环境、迁移覆盖风险、未选模块对已选模块的依赖 |

找不到信息时列出实际缺口，不要用 Todo、灵感等示例替代项目事实。

## 阶段二：让用户选择上云模块

根据扫描结果输出模块选择表：

| 模块 | 页面/文件 | 当前存储 | 被谁依赖 | 迁移影响 | 建议 |
|---|---|---|---|---|---|
| 实际模块名 | 实际路径 | 实际位置 | 页面或模块 | 读写/联动变化 | 上云、保留本地或需进一步确认 |

让用户明确选择一个、多个或全部模块。记录：

- 已选模块及其依赖模块；
- 未选模块如何继续读写；
- 是否需要把跨模块汇总、搜索、筛选或统计一起改造；
- 是否保留本地数据、导出能力和回退开关。

如果用户只说“把这个页面上云”，先确认页面实际依赖的共享数据，再给出最小可行范围，不擅自扩大范围。

## 阶段三：推荐数据库并确认页面访问

只针对已选模块比较方案：

### 文档型数据库

优先考虑 JSON/嵌套对象、页面状态、字段变化较快、关系简单、希望快速迁移的模块。说明集合、文档边界、主键、索引和单条/批量读写方式。

### MySQL

优先考虑实体关系稳定、多表关联、唯一约束、复杂筛选统计、事务或后续报表需求明显的模块。说明表、字段、主键/外键、索引和迁移脚本或 SQL 入口。

### 推荐格式

输出：

1. 推荐方案及依据；
2. 另一方案为什么不优先；
3. 对已选模块的模型草案；
4. 迁移成本、查询能力、权限和后续扩展影响；
5. 用户可以改选的明确入口。

默认一次改造使用一种数据库。只有模块之间存在明显不同的存储需求时，才提出混用，并说明额外的配置和维护成本。

确认页面可以直接从 `index.html` 或部署地址打开，并检查 CloudBase 的安全来源、域名和已有登录状态是否匹配。不要为了跨设备访问增加同步码、分享链接或额外入口；如果没有登录和权限隔离，仍要提示对应数据风险，不能把前端筛选当成权限控制。

## 阶段四：确认后实施

用户确认范围、数据库和页面访问方式后，再执行：

1. 先使用项目内官方 `cloudbase` Skill/连接器检查环境、数据库能力、认证、权限和部署入口；不要凭记忆臆造 CloudBase API 或密钥配置。
2. 列出将新增或修改的文件、云端集合/表/索引/规则、环境变量和部署配置。
3. 备份项目与选中模块的本地数据；保留原读取路径、导出能力或可切换回退方案，直到云端验收完成。
4. 让页面通过统一数据层读写已选模块。若当前没有数据层，先收拢已选模块的读写点；不要为了迁移无关页面而大范围重构。
5. 按已确认的文档型数据库或 MySQL 模型创建资源并执行一次迁移；迁移记录成功、失败和可回退动作。
6. 实现加载中、空数据、保存中、已保存、保存失败和重试等用户可见状态；失败时保留当前输入，不静默覆盖。
7. 保持未选模块原有行为，并测试它们与已选模块之间的联动是否仍符合预期。
8. 部署前检查安全来源、域名、认证回调、数据库权限和环境变量；不把 SecretId、SecretKey、服务端密钥或管理密钥写进浏览器代码、示例或提交。

## 阶段五：验收

根据用户选中的模块生成精确步骤，至少覆盖：

- 已选模块的新增、读取、编辑、删除或项目实际支持的对应操作；
- 刷新、重新打开和目标范围内的跨设备/跨会话恢复；
- 页面联动、筛选、统计和未选模块的原有行为；
- 保存失败、断网或权限拒绝时的提示、重试和数据保留；
- 迁移前后数据数量、关键字段和默认数据是否一致；
- 部署版本、环境和实际访问地址是否一致。

分别报告“已通过、未验证、失败及下一步”，不要把部署成功当成数据验收成功。

## 安全边界

- 不请求或输出管理密钥，不把密钥放进前端、日志、录屏或示例。
- 需要用户身份、私有数据隔离、团队协作、审计或敏感数据时，提出登录与权限方案；不要把直接访问 `index.html` 误表述为权限隔离。
- 不删除未备份的本地数据，不覆盖已有复盘结论；迁移失败时优先恢复原数据层。
- 只改用户确认的模块和必要依赖；额外重构、多人协作、离线冲突合并等需求另行确认。

## 交互示例

用户：把这个项目的客户列表页面数据存到 CloudBase。

先做：扫描整个项目，找出客户列表依赖的路由、数据读写、共享筛选和相关模块；输出模块选择表。然后让用户确认是否只迁移客户列表及其必要依赖，再推荐文档型数据库或 MySQL。确认后才列改动文件、数据模型、访问方式、迁移与验收步骤。

用户：我想让电脑和手机打开同一个工作台页面时看到同一份非敏感数据。

直接把数据读写改为 CloudBase，部署后让两台设备访问同一个 `index.html` 或部署地址。如果以后需要私有数据隔离，再单独接入登录和权限方案。
